## Search metadata

Keep `sitemap.xml` aligned with the canonical URLs of indexable public pages when
adding or removing pages. Use `https://raoventures.co/` for the homepage and link to `/`
rather than `index.html`. `robots.txt` advertises the sitemap to crawlers.

Each public page has a unique title, description, canonical URL, and social
preview metadata. The homepage includes Organization and WebSite JSON-LD; the
products page includes CollectionPage, BreadcrumbList, and ItemList JSON-LD.
Update the product list when released offerings change. Social previews use
the existing square logo with a summary card.

Robot Rescue Island is in beta and excluded from the sitemap, product structured
data, and marketing metadata. Its legal and support pages use `noindex`; the beta
section on the products page uses `data-nosnippet`. Keep these exclusions until
launch. Allow crawlers to access these pages so they can read `noindex`.

When replacing generated Ashtanga legal pages, preserve their SEO metadata and
page-level heading, or add these to the upstream generator before copying new
output. Keep the legal wording synchronized with the app sources.

After deployment, submit `https://raoventures.co/sitemap.xml` in Google Search
Console and check indexing and structured data there. Local checks cannot verify
Google's selected canonical URLs or search appearance.

### Source ownership and update workflow

The `ashtanga-yoga-app` repository is the source of truth for these legal documents. Keep its Spanish and Italian Markdown files even though the app's legal viewer displays English only:

- English sources: `docs/PRIVACY_POLICY.md` and `docs/EULA.md`.
- Spanish sources: `docs/legal/PRIVACY_POLICY.es.md` and `docs/legal/CONSUMER_TERMS.es.md`.
- Italian sources: `docs/legal/PRIVACY_POLICY.it.md` and `docs/legal/CONSUMER_TERMS.it.md`.

The English sources feed both the app's legal viewer (`src/data/legalDocsData.ts`) and the website generator. The Spanish and Italian sources feed the public website pages only; they are not imported into the app and do not translate its interface or legal viewer.

1. Edit and review the Markdown sources in `ashtanga-yoga-app`, keeping the language versions consistent.
2. Run `npm run build:legal` there. Its `scripts/build-release-legal.cjs` generates `release/legal/ashtanga-privacy.html` and `release/legal/ashtanga-eula.html`.
3. Copy both generated HTML files to this repository's root, preserving their filenames. Do not maintain separate legal wording by editing these generated copies independently.
4. Review and publish this repository through its website deployment workflow. Local generation and copying do not deploy the pages or release the app.

This repository hosts the generated pages at `https://raoventures.co/ashtanga-privacy.html` and `https://raoventures.co/ashtanga-eula.html`. Users select Español or Italiano on those pages, or follow the `#es` and `#it` links above. The `ashtanga-practice` marketing site links here rather than owning duplicate legal sources.

## Website analytics

The home and products pages load Vexo only after analytics consent. In Vexo, register
`raoventures.co` as a Web App domain. The SDK provides anonymous visitor/session
identity; use **Active Users** for unique visitors in the selected date range.
These counts cover consenting browsers and can change when visitors clear storage
or switch browsers/devices.

Use the **cta_click** custom event to measure CTA interactions, with `cta_id`
(the stable HTML `data-cta` value), `page_path`, `section`, `destination`, `target_url`,
and `text`. This covers navigation CTAs, hero/about buttons, product visits,
email/phone contact actions, and beta signup. Filter by `cta_id` to compare buttons
that share the same destination. External HTTP links also emit `outbound_click`;
these are separate metrics, so do not add both event totals to count CTA clicks.
URL query strings are excluded from custom-event destinations. Consented clicks
are queued in memory while the SDK downloads; navigation away before it finishes,
blocked scripts, or network failures can prevent delivery.

No visitor IDs or click events are created by site code before consent. Rejecting
or withdrawing consent disables the integration. App legal/support pages do not
load Vexo. Verify production events in Vexo after deploying; local checks cannot
confirm domain registration or ingestion.
